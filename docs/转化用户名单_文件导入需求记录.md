## 4. 转化跟踪：自动状态判断

转化跟踪表示转化商品的状态，文件没有直接对应列，后续按用户规则实现自动化。

| 状态 | 已确认的判断条件 |
| --- | --- |
| 待下单 | 商品已转化，转化下单量 = 0，且是否流失 = no |
| 下单中 | 转化下单量不为 0，且是否流失 = no；不再要求判断此前是否为待下单或是否为新增行 |
| 已流失 | 是否流失 = yes，但不满足下述“流失又回”条件 |
| 流失又回 | 是否流失 = yes，且最近下单的日历日期晚于流失日期，即至少是流失次日；流失当日下单仍为已流失 |

- yes 分支中，“流失又回”是“已流失”的例外，必须优先判断。
- “流失又回”不要求把是否流失改为 no。
- 不再用支付订单是否 > 0 来替代上述状态判断。
- 本轮定义的状态为：待下单、下单中、已流失、流失又回；旧选项“流失中”在V2.0中按当前订单和流失数据重算，不再作为自动状态。
- 比较最近下单时间与仅含日期的流失日期时，按统一业务时区的日历日期比较，不将流失日期简单视为当日零点来判回流。
- 导入日期缺失或无效时进入数据异常预警并暂缓，不伪造回流日期。
- 待下单和下单中按当前下单量及是否流失判断，不再额外限定旧状态。其他未定义的历史迁移细节不自行扩展。

## 7. 最后编辑时间

用户定义：每一行 CAM 最后一次操作或编辑的时间，覆盖程序自动更新和人工操作，不从文件抓取。

V2.0保留并实现该字段，采用以下方式：

- 新 CAM 插入时记入当前时间。
- 文件导入导致某行实际更新时，更新该行时间。
- 人工编辑某行并成功保存时，更新该行时间。
- 系统持久化修改某行状态等业务字段时，更新该行时间。
- 重复上传但该行没有变化、查看、筛选、折叠、普通渲染或动态时长显示时不更新时间。
- 自动保存时间不能递归触发更新时间；失败的编辑不记录成功修改时间。
- 设为系统只读字段，避免被人工改写为不真实的编辑时间。

## 9. 转化后持续出单时长

### 9.1 用户明确规则

- 沿用程序计算，属于系统派生字段。
- 新数据从第一次有效的“最近下单时间”开始计算。
- 第一次出单时固定起点，后续最近下单时间更新不重置起点；待下单阶段不累计。
- 直到转化跟踪变为“已流失”时停止计算。
- 已流失区间以流失日期作为结束点，而非程序发现流失或导入文件的时间。
- 进入“流失又回”后，从回流下单时间恢复累计，保留流失前的时长，排除流失期间；流失当日下单不触发恢复。
- 历史数据的第一次最近下单时间不清晰，暂以“转化时间”作为起点。
- 本轮没有要求以支付订单 > 0 作为计时前提；不能将旧实现中的支付门槛直接视为本轮新口径。

### 9.2 计算表达与剩余待确认项

- 持续出单时长 = 已结束的有效出单区间时长之和 + 当前未结束的有效出单区间时长。
- 流失期间不计入；回流后的计时起点一经记录，后续最近下单时间更新也不重置。
- 初次导入即为流失又回时，本文件不足以还原每次历史出单和流失区间，不得擅自推断完整历史。
- 文件有“首次下单时间”列，但用户指定的是“第一次最近下单时间”；不能未经确认用另一列替换。
- 当前按总有效区间折算完整天数；导入无效/缺失关键日期暂缓并提示，旧历史不足则使用估算。

## 11. 每日订单及相关字段更新

### 11.1 用户明确的订单更新规则

- 使用 CAMid（上传文件“广告id”）匹配已有 CAM。
- CAM 的最近下单时间、订单数变化时，填入新的时间和订单数。
- 更新列包括“最近下单日期”“转化下单量”“支付订单”。
- 两种订单量分别与历史值比较：最新值低于历史值，判为订单回退异常，将该 CAM 纳入预警中心。
- 用户要求每日更新两个订单量及其他涉及每日更新的列，具体8列清单由助手提出后用户已确认没有问题。
- 新 CAM 仍走新增流程；不以缺少某 CAM 的导入文件作为删除该 CAM 的依据。

### 11.2 已确认的更新字段清单

| 目标字段 | 更新来源或计算方式 | 状态 |
| --- | --- | --- |
| 转化下单量 | 下单总数 | 用户明确要求 |
| 支付订单 | 完成支付总数 | 用户明确要求 |
| 最近下单日期 | 最近下单时间 | 用户明确要求 |
| 是否流失 | 是否流失，yes/no 转为 是/否 | 用户已确认 |
| 流失日期 | 流失日期 | 建议同步，状态和时长计算依赖该字段 |
| 转化跟踪 | 基于更新后的下单量、是否流失、最近下单日期、流失日期，按第 4 节计算 | 已有规则，建议每次更新后联动 |
| 转化后持续出单时长 | 按第 9 节停止、恢复或持续累计 | 已有规则，建议联动 |
| 最后编辑时间 | 该行实际变更的时间，不使用文件最近下单时间代替 | 建议联动 |

- 这三个订单字段独立比较，不要求最近下单时间和订单数同时变化才更新。订单未变但流失信息变化也需要同步。
- 用户确认累计快照口径，以新值替换旧值，不逐次相加。
- 转化日期、年、季度不因订单更新而改变；用户身份、标题、国家、广告位、负责人、转化链接和转化原因是否随每日文件更新另行对齐。
- 人工复盘字段不建议被订单更新覆盖；此为更新保护建议，不扩展成已确认的所有字段更新策略。
- 在修改前保存被比较的历史值，以便预警展示旧值、新值和差额。

### 11.3 每日自动化的数据来源边界

- 最近下单日期代表最后一次订单时间，不等于数据快照生成时间，也不能单独证明数据是每日增量。
- 已确认以每天上传最新文件触发自动匹配、更新、计算及预警。
- 如要求每天无需上传即可定时更新，必须另行提供可读取的数据接口、同步文件位置或其他数据来源；目前未配置这些来源，不承诺后台定时自动抓取。
- 导入时间和文件名日期不足以证明文件数据比历史更新；如需要识别旧快照，建议提供明确快照时间。

## 12. 异常预警中心入口

用户截图指向“转化用户名单”页右上角现有“流失待分析”警铃按钮，位于“清空全部筛选”和“导出筛选结果”之前。

### 12.1 用户明确要求

- 该位置扩展为异常预警中心入口，承接不同类型的 CAM 问题。
- 订单回退显示“异常订单预警”等相应文案，不能仍统一称为“流失待分析”。
- 原有流失待分析入口功能需纳入同一中心。
- 点击处理/查看沿用现有定位逻辑：关闭弹窗、进入名单页、切换目标年份、展开月份、必要时清除遮挡目标的字段筛选，滚动并高亮目标 CAM。

### 12.2 界面与记录实现方式

- 只有一种预警时显示对应名称，多类型并存时入口显示“异常预警中心”，弹窗内按类型筛选。
- 预警列出 CAM、问题类型、相关字段、历史值、新值、差额、发现时间，并提供“查看”。
- 同一 CAM 同时有下单量和支付量回退时聚合展示，避免重复刷屏。
- 建议入口角标按存在未处理预警的 CAM 去重计数；弹窗中可显示具体预警项数。
- 订单回退事件不能只靠当前字段重新计算，否则写入新值或刷新后丢失历史对照；建议本地持久化预警事件。
- 相同异常在同一快照重复导入时避免重复生成；历史对照和重复检测需明确快照标识。
- “查看”只定位，不自动视为已解决。解决、忽略、恢复及人工确认的流程尚未定义。

## 13. 异常检测建议

订单回退为用户明确的异常规则。用户最终确认以下其他异常全部设置，V2.0 已启用。

| 类型 | 判定示例 | 建议处理 |
| --- | --- | --- |
| 订单回退 | 新下单总数或新完成支付总数 < 当前已保存值 | 纳入异常订单预警，保留前后对照 |
| 订单值无效 | 负数、小数、无法解析的文本 | 不把无效值转为 0，提示对应字段 |
| CAM 标识异常 | 空 CAMid、重复 CAMid 且记录内容冲突 | 提示导入异常，不随意覆盖 |
| 最近下单时间回退 | 新的最近下单时间早于已保存时间 | 提示日期回退/疑似旧快照，不直接证明为旧文件 |
| 日期逻辑异常 | 最近下单早于转化、流失早于转化、日期无法解析 | 提示时间线异常 |
| 流失信息缺失 | 是否流失为 yes，但流失日期为空或无效 | 提示无法准确计算回流与出单区间 |
| 关键更新字段缺失 | 有 CAMid，但订单量列缺失/空白，或已有日期被占位符替代 | 提示缺失，不将缺失数据误当成 0 或自动清空历史 |
| CAM 身份冲突 | 同一个 CAMid 对应不同用户ID | 提示匹配冲突，不任意改变 CAM 归属 |
| 支付量大于下单量 | 完成支付总数 > 下单总数 | 用户确认全部设置，作为待复核提示，不自动判断具体原因 |

- 同一时间订单量增加未必异常（累计支付等可能延迟更新），不仅因时间未变而报警。
- 下单和支付订单量下降按本需求报警；原因可能涉及源数据修正、取消或统计调整，预警文案不能擅自宣称具体原因。
- 是否保留现有支付订单单次 +40 的增长提示、是否纳入中心及阈值如何调整，待确认，不将增长默认视为错误。

## 14. 本轮最终确认与实现边界

用户已确认：

- 每天上传最新文件后自动匹配更新，不接入外部定时抓取。
- 其他异常全部设置。
- 订单回退需人工确认后才更新；确认前保留原值。
- 日更8列清单及累计快照更新口径没有问题，可以进入开发。

V2.0 落地方式：

- 上传先预览，点击导入后正常行自动更新，异常行暂缓。
- 可复核异常整行暂缓，确保订单、流失信息、状态和计时不会部分错配；确认时一并应用5个文件日更字段并重新计算派生字段。
- 无效值、缺失关键日期、身份冲突及矛盾时间线需修正后重传，不能用确认按钮绕过。

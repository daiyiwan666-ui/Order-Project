# Supabase 联网协作版实施方案

日期：2026-10-20。基于已发布的 V2.0.0。

状态：V2.1.0-beta.2 已接入账号、成员、人工读写和云端文件导入/预警。真实管理员登录、人工备注保存及刷新读取已验收，云端上传已通过数据库与模拟浏览器验证，实际网页上传待验收。未迁入正式数据；服务端分页汇总、实时同步、订单推品编辑和备份恢复尚未完成。范围见 [云端导入与预警说明](Supabase_云端导入与预警说明.md)。

## 一、目标与顺序

目标为 3–4 人使用同一个网页、共享查看和修改不超过约 1 万条 CAM 主记录，优先使用 Supabase 免费套餐。

五个交付目标不变：云端保存、账号登录、多人编辑保护、分页查询、备份恢复。实际顺序如下：

1. 检查目标项目的状态、已有表、已有数据和认证配置。
2. 创建业务表、约束、成员权限、并发版本和索引；再实现受版本检查保护的服务端业务操作。
3. 接入指定成员的账号登录，以及网页对云端数据的读写。
4. 联调多人修改、批量导入、预警确认、分页和变化同步。
5. 迁移确认的数据来源，配置备份并做恢复验证，再切换正式使用。

备份方案在第二步一并设计；在迁移正式数据之前应具备可用备份，不等正式使用后再补。

## 二、已建立的数据表

| 表 | 职责 |
| --- | --- |
| app_members | 允许访问本项目的登录成员、显示姓名和角色 |
| cams | 转化用户名单主表，CAM 唯一，保存当前业务数据 |
| order_projects | 订单推品项目数据，避免另一个数据源仍停留在个人浏览器 |
| import_batches | 文件摘要、导入人、时间、处理结果，用于重复导入和追溯 |
| alerts | 共享预警、候选变更、原记录版本和处理状态 |
| cam_order_periods | CAM 有效出单区间及历史估算标记 |
| audit_events | 谁在何时修改了哪些字段及修改前后值 |

登录账号使用 Supabase Auth。app_members 关联 auth.users 的 UUID；Excel 中 user_id 是业务用户编号，两者不能混用。

不把每天整张表复制保存为一份新主表。主表保持最新值，历史表保存必要变化，后续根据实际用量确定归档策略，不默认删除历史。

## 三、字段和时间设计

- CAMid、业务用户ID按 text 保存，保留长编号精度；CAMid设置唯一约束。
- 保留 V2.0 可见的 27 个业务字段及分析所需的隐藏源字段，页面继续使用中文字段名。
- 多值标签保留数组语义，不能在迁移中意外改成只能保存一个标签。
- 订单量保存非负整数，空值与真实的0保持区别。
- 是否流失保存单一布尔状态；转化跟踪由业务规则派生，不允许写入互相冲突的多个状态。
- 转化日期、最近下单日期、系统编辑时间使用有明确时区的时间戳；流失日期使用date。
- 源文件无时区的时间按Asia/Shanghai解释；数据库保存标准时间，页面按业务时区显示，不能沿用浏览器中的伪UTC时间戳直接入库。
- 回流判断按Asia/Shanghai的日历日期比较，同日仍为已流失。
- row_version由数据库维护，updated_at和updated_by由服务端记录。
- 持续出单时长从有效区间计算，不每分钟把所有CAM写入数据库。

## 四、成员和权限

- 仅允许 app_members 中的有效成员访问业务数据；注册账号本身不自动获得项目权限。
- 建议角色为管理员、编辑者、查看者；成员维护只由管理员完成。
- 对业务表启用RLS，未登录和非成员不能读取或修改数据。
- 可编辑字段与派生字段分开。导入、预警确认、状态计算和计时区间变更在受控的数据库函数或服务端操作中执行。
- 网页仅使用适合公开的项目配置和客户端密钥，不在公开GitHub源码中放管理密钥或数据库密码。
- 连接开发工具的Supabase授权，与最终网页用户的登录权限分别配置。

## 五、并发及导入一致性

- 每次编辑提交CAM、修改字段和expected_version，不再上传整份users数组覆盖共享数据。
- 数据库只在版本匹配时更新；冲突返回当前值，由页面提示重新核对。
- 修改业务数据、最后编辑时间、操作记录和出单区间时保持事务一致性。
- CAM业务规则在服务端再次验证，不能依赖浏览器预览中的判断结果。
- 新CAM按唯一约束新增；已有CAM继续只更新V2.0确认的5个文件日更字段，并联动派生字段。
- 人工备注等字段不被日更覆盖。
- 订单回退等异常先登记共享预警，人工确认前不改原值。
- 确认预警时再次核对候选对应的记录版本；另一个成员已更新过则拒绝过期候选。
- 预警只能被成功处理一次，防止两位成员同时确认。
- 导入按批处理，仅写入实际变化的行，文件摘要用于识别重复上传；失败行和成功行给出明确结果。

## 六、分页、筛选与分析

- 名单使用服务端分页，建议每页50或100条；保留年份、月份和字段筛选体验。
- 候选筛选计数按完整筛选范围计算，不仅统计当前页。
- 看板、Trigger等汇总按完整筛选范围计算，不把当前页误当成全量数据。
- 导出覆盖完整筛选结果，不只导出当前页。
- CAM定位根据年份、月份和排序定位目标页，继续高亮目标记录。
- 变化同步以必要通知和增量读取为主；批量导入不让每个成员反复下载整表。
- 同步中断后重新核对服务器状态，页面明确展示保存中、已保存和失败状态。

## 七、迁移与备份

- 正式迁移前确定哪份浏览器数据或Excel为权威来源，先备份，再迁移。
- 不自动把内嵌15条演示样例写成正式业务数据；不将不同浏览器的数据直接无条件合并。
- 迁移时保留已确认的人工字段、预警处理结果及有效出单区间，不重新猜测已经记录的历史。
- 备份覆盖业务主表及关联的导入、预警、区间、审计数据，不仅导出名单的27个字段。
- 提供手工完整备份入口，再配置定期备份；恢复先在测试环境验证。
- 项目GitHub仓库是公开仓库，数据库备份不提交到该仓库。自动备份的私有存放位置在接入时确定。
- 免费版的暂停、容量和流量限制通过用量监控及备份策略管理，不承诺永久免费或免费版自动数据库备份。

## 八、验收重点

1. 未登录及非成员访问被拒绝，授权成员可按角色读写。
2. 两个账号同时修改同一CAM，不发生静默覆盖。
3. 一个账号上传或确认预警后，另一账号能看到结果。
4. 断网或保存失败有明确提示，不能显示为成功保存。
5. 多人同时导入或确认不会重复新增CAM、重复处理预警或错配人工字段。
6. 1万行场景下分页、完整范围汇总、筛选计数、导出和CAM定位正确。
7. 完整备份可恢复且关联数据一致。
